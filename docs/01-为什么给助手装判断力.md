# 01 · 为什么给助手装一个"判断层"

> 你的 AI 助手每天都在做几十个"小决定"。这篇讲清楚：为什么这些决定值得单独交给一个"小判定器"，以及它和"换更大的模型"根本不是一回事。

## 你的助手每天都在做几十个小决定

随便列举一个真实工作日下午的片段：

- 这条命令要不要拦一下？（`rm -rf` 出现在一段脚本里，是常规清理还是危险操作？）
- 搜索回来了 22 条结果，**先读哪 5 条**？
- 记忆库里召回了 12 条资料，**哪几条和当前任务真的相关**？
- 上下文快满了，压缩时**哪些片段必须原样保留**（关键约束、用户偏好）？
- 用户这句"帮我看看"，是要**干活**、要**查资料**，还是只是**随口一说**？
- 手头有两个技能都沾点边，**用哪个更合适**？

这些决定单个都不难，**但架不住量大**——而且每一个都在消耗大模型的"注意力预算"。

## 两条老路，都不太通

**路一：全部交给大模型。**
贵：每个小决定都烧一遍完整推理。慢：每个小决定都要等一次生成。分心：大模型把注意力花在"拦不拦命令"上，真正干活的部分就少了。还有一个隐蔽问题——**大模型不给"把握度"**。它会用同样笃定的语气说「这条命令很危险」和「可能有点风险」，你的代码没法拿它做概率判断。

**路二：写死规则。**
正则、关键词、if-else。写得完吗？写不完。改得动吗？一改就动全身。遇到边界情况呢？只会错给你看。

## 第三条路：一个"只做判断"的小模型

这就是 Jev（TypeSafe 的 System One 模型）的思路——**不聊天、不写作、只回答小问题**：

| 它回答的问法 | 返回什么 | 例子 |
|---|---|---|
| **是 / 否**（noul） | 一个 0–1 的概率 | "这条命令危险吗？" → 0.12 |
| **选一个**（choice） | 选中的选项 + 各选项概率 + 置信度 | "这 22 条里先读哪条？" → #7（0.83） |
| **打个分**（score） | 按你定义的档位打分 + 各档位概率 + 置信度 | "这段信息多重要？" → 2.1/3 |

关键特性：

- **答案是结构化的**——你的代码直接 `branch / sort / route`，不需要解析自然语言；
- **概率是有意义的**——0.72 就是"十次里大约七次成立"，可以设阈值、可以校准；
- **又快又便宜**——一次请求亚秒级到几秒；一个问题问一批（一个请求里可以并列很多小问题，几乎不增加耗时）；
- **原子化**——"问一个具体、边界清楚的小问题"是使用它的正确姿势；复杂判断拆成多个小问题，在代码里加权合并。

## 把它放在哪些位置（我们的地图）

| 位置 | 问什么 | 答案怎么用 |
|---|---|---|
| 搜索结果返回后 | "这条结果与问题的相关度？" | 预排序，先读最相关的几条 |
| 工具执行前 | "这个操作有破坏性吗？"（影子模式） | 高风险才提请确认 |
| 记忆/资料召回后 | "这条资料值得进上下文吗？" | 筛掉冗余，保住上下文预算 |
| 上下文压缩时 | "这段必须保留吗？" | 保住关键约束不被压掉 |
| 批量小决定 | "这批条目各自属于哪类？" | 一次请求分完，代码归类 |

## 最重要的心法（先记住这三条）

1. **它是一把锋利的尺子，不是更聪明的脑子。** 问题要剪小、剪具体——"帮我判断一下这堆东西重不重要"不合格，"这条资料对『给水管道设计』这个任务的重要度打个分"才合格。
2. **一个请求可以问一批小问题。** 把同一次决策里要问的五六件事打包成一次调用，并行评估。
3. **它的答案是要喂给代码的**，不是给人读的作文。你写的是 `if probability > 0.8:`，而不是把答案转述给用户。

## 小结

- 小决定 → 判定器（快、省、可校准、结构化）；
- 大活 → 大模型（写作、推理、综合）；
- 红线 → 永远是人（花钱、发布、删除）。
- 三者各就各位，助手才不掉链子。
