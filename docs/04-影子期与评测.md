# 04 · 影子期与评测：先确认靠谱，再一步步放权

> 这是整本手册里最重要的一篇，也是很多"接判定器"项目翻车的地方：
> 直接上线 → 出了几次错 → 觉得"不可靠" → 全部撤掉。
> 正确姿势是 **影子期 → 族级评测 → 逐族放权**。

## 第一步：影子模式（只记录，不拦截）

新的判定点，**第一周永远从影子模式开始**：

- 每次本该"由它做决定"的时刻，**照样走老逻辑**；同时把**它的判断**记录进账本；
- 不改变任何实际行为——它说什么都只进日志；
- 一周后，把账本和实际发生的事对照：
  - 它说"危险"的操作，事后看真的危险吗？
  - 它说"先读第 7 条"，第 7 条真的有价值吗？

**这一步的意义**：你积累的不是"感觉"，是**可数的样本**。

## 第二步：按"任务族"分别评测（关键！）

**千万别把所有判断混在一起统计一个总准确率。**

同一个"命令危险吗"的判定点，在不同场景下可能表现天差地别：

| 任务族 | 例子 | 我们观察到的可靠度 |
|---|---|---|
| 明显的删除/覆盖类 | `rm -rf`、覆盖系统目录 | 很高（接近总是对） |
| 开发日常类 | 构建脚本里的临时目录清理 | 高 |
| 灰区类 | "看起来像但要结合上下文"的复合命令 | 明显下降，**需要人复核** |
| 边界罕见的族 | 少见工具/管道组合 | 低——**不放权，继续影子或直接走人工** |

我们踩过的真实教训：**汇总统计时看到"90% 准"，就兴冲冲放权；结果错的都集中在灰区那一族**——而对用户来说，"偶尔拦错关键操作"的代价远大于"多拦几次"。

**族级评测的做法**：
1. 给账本每条记录标上**任务族**（自己在建账本时也记一份"这题属于哪族"）；
2. 按族算命中率和"错的方向"（误报 vs 漏报分别算）；
3. **逐族定放权阈值**——达标的族先放权，不达标的继续影子。

## 第三步：阈值与"置信度是第二道闸"

- 放权不是全有全无：常见做法是**双阈值分档**——
  - 概率 ≥ 0.9：自动执行；
  - 0.5–0.9：执行但记重点日志（或提示一下）；
  - < 0.5：**交给人/走老路径**。
- **置信度（confidence）是另一根轴**：答案告诉你"它选什么"，置信度告诉你"它有多敢下这个结论"。
  - 实测非常好用：模棱两可的问题上，它会给**接近 0 的置信度**——等于主动喊"这题我拿不准"；
  - 代码里把低置信度路由到人工，是性价比最高的一招。

## 第四步：选项设计会直接影响判别力

实测教训：**同样的问题，选项写得含糊，判别力会明显下降。**

- ❌ "选一个：重要 / 不重要"——太粗；
- ✅ "选一个：直接回答问题的数据 / 只说相关领域没有数据 / 跑题"——**每个选项自带判别依据**（choice 的 criteria 就是给这个用的）；
- 打分题（score）把档位写成**一句话级别描述**，别只写"低/中/高"。

## 第五步：账本字段建议

| 字段 | 为什么 |
|---|---|
| 时间 | 复盘、算漂移 |
| 判定点 + 任务族 | 族级评测的必需项 |
| 输入摘要（脱敏） | 复盘时看上下文 |
| 判定答案 + 概率 + 置信度 | 后续校准阈值 |
| 实际结果（事后回填） | 命中率的"真值" |
| 兜底是否触发 | 评估失败安全 |

## 一个反直觉但重要的提醒

**别指望"评测一次就完事"。** 模型的版本会迭代、你的场景会漂移。把账本做成**常开**的：每周扫一眼各族的命中率，掉了就回退到影子/人工。
